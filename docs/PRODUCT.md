# PRODUCT.md — Micro Survivor（仮題）

> **文書ステータス**: MVPプロダクト仕様 v0.1（2026-10-09）  
> **対象**: Steam向けWindows PCゲーム  
> **この文書の役割**: 「何を、誰のために、どこまで作るか」を定義する。ゲーム内ルールの詳細は [`GAME_DESIGN.md`](./GAME_DESIGN.md) を参照。  
> **決定事項と提案値の区別**: **[確定]** は会話で採用された方針、**[MVP決定案]** は実装開始時の基準、**[検証待ち]** は技術スパイクやプレイテストを要する項目。

---

## 1. プロダクト概要

### 1.1 ワンセンテンス

Pythonでスライムの行動をプログラミングし、四方から迫る細菌の群れを60秒生き延びる、コード駆動型2Dオートサバイバルゲーム。

### 1.2 プレイヤーへの約束

- 自分で書いたコードによって、スライムの行動が実際に変わる。
- シンプルな数行のプログラムでも遊べるが、アルゴリズムを工夫するほど高度な攻略を目指せる。
- 戦闘中に移動・攻撃を直接操作しない。考える・書く・観察する・改善することが遊びの中心になる。
- Pythonの事前知識がなくても開始でき、強制的な文法テストなしに必要な構文を自然に身につけられる。
- ゲームそのものが面白いことを最優先し、「教育ゲーム」という見せ方は押し出さない。

### 1.3 企画の位置づけ

『The Farmer Was Replaced』の「コードによって挙動を自動化・改善する楽しさ」と、見下ろし型サバイバルの「周囲の敵に対して判断する面白さ」を掛け合わせる。『皿打』からは、周囲から敵が迫る、直感的に状況がわかる雰囲気を着想として取り入れる。既存作品の名称・アート・固有演出・ゲームデータは流用しない。

**仮タイトル**は「Micro Survivor」。正式タイトル、アートスタイル、価格はMVP後に検討する。

## 3. 想定ユーザーと価値

### 3.1 Python未経験者

- 「Run」を押すだけでスライムが戦うところから始められる。
- 動くサンプルコードの数値を変える → 条件を変える → ループや関数を使う、という小さな成功体験を積める。
- 用語の説明を読まなくても遊べる。説明やヒントは困ったときだけ開ける。
- 構文エラーを恐れず試せる。エラーを該当行とともに示し、即座に再実行できる。

### 3.2 Python経験者

- 自分の探索・予測・リスク評価・ターゲット選択アルゴリズムを実装できる。
- 関数、クラス、内包表記、複数ファイルなど一般的なPythonの書き方を活かせる。
- 高水準の便利APIを使わず、低水準の状態取得・移動指示から制御できる。
- 60秒クリア後も、残存HP・撃破数・被ダメージ・コードの単純さなど、自分で目標を設けて改善できる。

### 3.3 両者に共通すること

プレイヤーの成功は「指定の文法を書いたか」ではなく、「スライムが結果として生き残ったか」で評価する。特定の構文・アルゴリズム・クラスの利用をクリア条件にしない。

## 4. プロダクトの柱（優先順位順）

1. **コードがゲームへ伝わる手応え**: 変更した命令が行動や結果に明確に反映される。
2. **試行錯誤の気持ちよさ**: 書く → 実行 → 観察 → 改善が短く、失敗から学びやすい。
3. **戦略の自由**: 一つの正解に閉じず、回避・撃破・距離維持など異なる解が成立する。
4. **初心者でも始められる**: 動くサンプル、段階的な任意ヒント、わかりやすいログ。
5. **自分の開発環境を作る楽しさ**: ゲーム全面の上に、複数のコードウィンドウを自由配置できる。

**アンチゴール**: 文法を暗記させる小テスト、穴埋め必須、進行するための強制講義、特定解法の押し付け、見た目優先でプログラミング体験を後回しにする開発。

## 5. MVPで提供する体験

### 5.1 初回起動〜クリアまで

1. タイトルから「はじめる」を選択する。
2. 画面全体に微小世界のアリーナが表示される。画面上にはサンプル入りの `main.py` エディタを1枚開く。
3. 「Run」で開始すると、サンプルPythonに従ってスライムが敵を狙う。
4. 敵の増加で攻撃一辺倒では苦しくなり、回避条件などを試したくなる。
5. 「Stop / Restart」で初期状態へ戻し、コードを修正して再挑戦する。
6. 60秒生き残ればクリア。死亡した場合は生存時間などを確認して再挑戦する。
7. 上級者は `utils.py` 等を追加し、複数エディタを並べてアルゴリズムを改善する。

### 5.2 最小ゲームプレイ

- 主人公: スライム1体。
- ステージ: 固定アリーナ1種類。
- 敵: まず追跡型を実装し、MVP内では高速型を追加する **[MVP決定案]**。
- 目標: 60秒生存。HPが0になれば失敗。
- 基本行動: 任意方向への移動、敵の指定、射程内での攻撃。ゲーム側が攻撃間隔を管理する。
- プレイヤー入力: 戦闘を動かすコードのみ。マウス・キーボードによる手動戦闘操作なし。
- 結果表示: クリア/失敗、生存時間、撃破数、残りHP、被ダメージ。
- 構文の合否判定、成績に基づく学習ランク、オンラインランキングは設けない。

### 5.3 対象プラットフォーム・入力

- Windows 64-bit、キーボード・マウスを主対象とする。
- 配布物はオフラインでも起動・プレイできることを目標とする。
- Steam実績・Steam Cloud・オンライン同期・アカウント登録はMVP対象外。
- スマートフォン・ゲームパッド・多言語同時ローンチはMVP対象外。

## 6. プログラミング体験の要求仕様

### 6.1 Pythonを使う意味

単なる命令の選択肢を並べるのではなく、プレイヤーが変数・条件分岐・反復・関数・クラス・データ構造・探索などを組み合わせて行動AIを作れることを重視する。

### 6.2 二層API

- **初心者向け高水準API**: 「最も近い敵を攻撃」「この敵から遠ざかる」などを短く表現できる補助機能。
- **上級者向け低水準API**: 敵一覧、座標、HP、距離などを観測し、移動方向・攻撃対象を直接指定できる機能。
- 高水準APIは低水準APIの組み合わせとして説明可能であり、上級者の独自処理を妨げない。

### 6.3 二つの実行スタイル

- **判断関数型**: `decide(state)` の戻り値で次の行動を指示。クラスによる状態保持にも対応。
- **継続実行型**: `while`・`wait_ticks()` を用いて状態を確認しながら命令。ユーザーコードの状態を維持する。
- 双方が同じゲーム内行動仕様へ変換され、ゲームの内部状態を直接書き換えられない。
- 1体のスライムに同時に2系統の行動命令が競合しないよう、制御権を明確化する。
- **[検証待ち]** Pyodide上での一般的なPython構文、継続実行の中断・再開、停止、安全性、決定論を技術スパイクで確認する。条件を満たせなければ実装方式を変更し、ユーザー体験上の要件は維持する。

### 6.4 Python自由度の方針

- 基本構文、関数、クラス、辞書・リストなどを制限する理由は原則設けない。
- Python標準ライブラリの対応範囲は実行環境と安全性を基に明示する。`math`など計算用途を優先する。
- プログラムの複数ファイル化とゲーム内 `import` をサポートする方針。
- OSファイル・外部ネットワーク・無制限の外部依存導入は提供しない。
- 実行時間・メモリ使用量・ゲームAPIアクセスは安全性と公平性のため管理する。
- 「完全な任意Python互換」や悪意あるコードに対する完璧な隔離は、技術検証前には約束しない。

### 6.5 初学者を支援する機能

- 初期状態に、すぐ実行できる動作例を用意する。
- オプションのヒントは「何を試してみよう？」と具体的な目標を示し、文法講義を前面に出さない。
- `SyntaxError` や実行時例外が起きたとき、可能な限りファイル名・行番号・内容を見せる。
- コード編集を停止中に行い、Restartで同じ場面から再挑戦できる。
- 説明は任意で開けるAPIヘルプに置き、プレイを妨げる強制ポップアップを避ける。

## 7. 画面・操作体験

### 7.1 基本構成

- **ゲームキャンバスが常にアプリ画面全体を占める**。左右固定分割にしない。
- Reactがゲーム画面上に仮想ウィンドウを重ねる（ElectronのOSウィンドウをファイルごとに増やさない）。
- `main.py`、`utils.py`、`strategy.py` など複数の `.py` ファイルをそれぞれエディタウィンドウで開ける。
- エディタの数は小さな固定上限を設けず、実際の動作性能で制御・最適化する。
- ドラッグ移動、リサイズ、最前面化、最小化、閉じる、再表示をサポートする。
- 閉じてもファイルの内容は削除しない。ウィンドウ配置を保存・復元する。
- カメラは広範囲のズームとパンに対応。ズームはゲーム世界にのみ作用し、エディタの位置・文字サイズは変わらない。
- ゲーム画面がエディタに隠れたら、ユーザーがズーム/パンで視認性を確保できる。スライムへカメラを戻す操作を提供する。
- ステータス表示（HP・経過時間・撃破数）、実行コントロール、ログパネルもゲーム上に重ねる。

### 7.2 UIで最優先すること

- コードウィンドウを置いたまま戦闘を見ることができる。
- キーボードフォーカスがエディタにある間、カメラ操作と衝突しない。
- エラーが起きてもコードやウィンドウ配置が消えない。
- 複雑なスライム/細菌のアートは要求しない。色・形・動き・射程・危険度が読める方を優先する。

## 8. フィードバックとリプレイ性

- 決定論的ステージなので、**同じコード・同じ初期状態・同じ実行環境と許可された入力なら同じ結果**を目指す。
- MVPではseed変更UIなし。敵の出現・乱数はステージ固定seedから決める。
- クリア条件は60秒生存の一つに絞る。成績は数値として見せるが、複雑な総合点は導入しない。
- プレイヤーが条件式やアルゴリズムを改善した結果を比較しやすいよう、再挑戦時には戦闘を初期状態から再現する。
- カメラ位置・ウィンドウ配置などのUI操作は戦闘結果に影響しない。

## 9. MVPの範囲

### 9.1 必須（P0）

1. Windows上で起動するElectronアプリ。
2. Phaserによるフルスクリーン相当の2Dプレイ画面とズーム/パン。
3. React製の自由配置・リサイズ可能な複数エディタウィンドウとMonaco。
4. `.py`ファイルの作成、保存、再表示、エントリーポイント `main.py` の実行。
5. Python判断関数型の動作、継続実行型の動作と停止。両方のスタイルを使えること。
6. 移動・攻撃・被ダメージ・敵出現・HP・死亡・クリア。
7. 固定30 tick/秒を初期案とするシミュレーション、固定seed、再実行の再現性。
8. 実行/停止/一時停止/再開、ログ、エラー表示。
9. 1体・1ステージ・60秒生存ゲーム、クリア/失敗の結果画面。
10. コードとウィンドウ配置のローカル保存、オフライン起動、Windows配布ビルド。
11. GitHub Actionsでの基本テスト、シミュレーションの再現性テスト。

### 9.2 できれば入れる（P1、P0完了を優先）

- 初心者向け任意ヒント。
- APIをゲーム内で検索できる簡易ヘルプ。
- 2種類目の敵（高速型）、色とアニメーションの改善。
- 戦闘中のどのtickで何をしたかを追える簡易デバッグ表示。

### 9.3 MVPに入れない

- 複数スライムの協調AI、本格的な進化・装備・育成。
- 複数ステージ、大規模マップ、ランダムseedのチャレンジモード。
- 対人対戦、クラウド処理、サーバーサイドPython実行、オンラインランキング。
- ログイン、課金、ショップ、Steam実績/Cloud。
- 複雑なピクセルアート、ストーリー、フルボイス、外部ライブラリの自由インストール。
- 自動AIヒント生成やLLM連携（将来候補）。

## 10. 非機能要求

### 10.1 安定性・再現性

- 同一リビジョン・同一実行環境で初期状態と行動列が等しければ状態系列が一致する。
- 許可したPython操作でも再現性を損なわないよう、時刻・乱数・ファイル・通信への依存を制御する。
- コードの無限ループ・エラー・重い計算はアプリ全体を停止させないよう、Pythonランタイムを分離する。
- Python異常終了後もエディタのコードを保持し、リセットして再挑戦できる。

### 10.2 セキュリティ

- ElectronのレンダラにNode.js権限を直接与えない。権限の小さいpreload APIを介して保存等を行う。
- ユーザーPythonをゲーム内部と分離し、ゲームAPIを通した入力・出力だけを許す。
- Pythonからの任意ネットワーク要求・OSファイルアクセスをMVPでは提供しない。
- **[検証待ち]** Pyodide/Web Workerを安全な完全サンドボックスと見なさず、実現可能な制限と残存リスクを `SECURITY.md` で検証する。

### 10.3 性能・UX

- Windows一般的なPCで滑らかな2Dゲーム表示を目指す（描画目標60 FPS、論理30 tick/秒は別概念）。
- 初回起動・再実行・Python起動待ちには進捗を示し、UIを固めない。
- エディタを複数開いても入力操作が実用的な速度を維持すること。
- アセットやPython実行環境はインストール物に同梱し、MVPはオフラインで完結する。

### 10.4 保存・プライバシー

- コード・設定・ウィンドウレイアウトはローカル保存を標準とする。
- エディタのファイルを閉じてもコードは削除しない。
- 意図せぬ送信や自動テレメトリーはMVPでは実装しない。

## 11. MVPの受け入れ条件（プロダクトレベル）

- [ ] 新規プレイヤーがPythonの知識ゼロでも、サンプルを実行してスライムが戦う様子を見られる。
- [ ] サンプルのしきい値を変えると、同じステージでもスライムの行動が変化する。
- [ ] 自作の関数/クラスで行動戦略を実装できる。
- [ ] 継続実行型と判断関数型の双方で1ステージをプレイできる。
- [ ] `main.py` 以外の `.py` を作り、importして利用できる。
- [ ] 複数エディタの位置・サイズを自由に変えられ、ゲーム画面は背後に途切れず存在する。
- [ ] 広域ズーム/パン操作でスライム周囲を見やすくでき、カメラ操作ではシミュレーションが変化しない。
- [ ] 同じコード・固定seed・同じ実行環境で複数回Restartすると戦闘結果が再現する。
- [ ] Python例外や無限ループでElectronアプリがクラッシュせず、実行停止・再挑戦が可能。
- [ ] Windows配布ビルドを新規環境でオフライン起動してプレイできる。
- [ ] 60秒生存時にクリア、HP0時に失敗、結果表示と再挑戦が可能。
- [ ] Pythonの特定構文を使わなくても、プレイ結果によってクリアできる。

## 12. 主要リスクと検証順序

| リスク | 初期対策 / 判断ゲート |
|---|---|
| 任意の `while` / クラス / 再帰と実行停止を両立しにくい | **最初に**Pyodideの技術スパイク。成立しなければランタイム/スケジューラを再選定 |
| Pythonを自由にすると決定論が破綻する | 時刻・乱数・I/Oの仕様を限定し、固定入力での再現テスト |
| Pythonからゲーム外権限に触れてしまう | Electron権限分離、Worker、依存制限、実行停止の検証 |
| 自由配置ウィンドウがゲームを隠す | ズーム、パン、フォーカス復帰、レイアウト保存 |
| 初心者が何を書けばよいかわからない | 最初から動くコードと任意ヒント。エラー位置の提示 |
| 上級者にはゲームが単調 | 低水準APIを公開し、複数の勝ち筋と改善余地を確保 |
| 機能が膨張して完成しない | 1体・1ステージ・60秒に固定。P1/P2を明確に分離 |
