## 1. ゲームの核

### 1.1 ゲームループ

```text
コードを書く / ファイルを分割する
          ↓
実行してスライムの行動を観察
          ↓
敵に追われる・攻撃される・生き残る
          ↓
結果（生存時間・撃破数・HP・ログ）を確認
          ↓
行動ロジックを改善 → 同じステージで再挑戦
```

- プレイヤーはスライムを直接移動させない。
- コードの試行錯誤が主なプレイヤー行動である。
- UIは「全画面の戦闘フィールド + 自由配置のコードウィンドウ」で構成する。
- 面白い攻略を目指す過程でPythonを自然と使う。文法学習が表面上の目的ではない。

### 1.2 基本勝敗ルール [確定]

- 1ステージ、スライム1体、制限時間60秒。
- 60秒経過時点でスライムのHPが1以上なら成功。
- HPが0以下で失敗。途中でStopした場合は中断であり、失敗記録として扱わない。
- 最終tickでHPが0になった場合は失敗（攻撃・ダメージの適用後に終了判定）。
- ステージに紐づいたseedは固定で、MVPにseed選択UIを用意しない。
- クリアにはPythonの特定の書き方を要求しない。

## 2. ゲームワールド

### 2.1 表示とワールドの区別

- **ワールド座標**はゲーム世界内の位置。描画のピクセルや画面のズーム倍率と切り離す。
- **カメラ**はワールド座標を画面座標に変換する表示装置であり、シミュレーションに影響しない。
- **エディタ**はカメラの外側にあるReact UIで、ズームしても文字や位置は変わらない。

### 2.2 アリーナ [初期値案]

| 項目 | 初期値案 | 補足 |
|---|---:|---|
| ワールド寸法 | 2400 × 1600 world unit | 比率はプレイテストで調整 |
| 初期スライム位置 | 中央 (1200, 800) | 固定 |
| ワールド境界 | 通過不可、位置をクランプ | ワープなし |
| 障害物 | なし | MVPでは衝突・経路探索を単純化 |
| 背景 | 淡色の単色 + 薄いグリッド | 顕微鏡下をイメージ |
| カメラ倍率 | 0.15〜4.0倍 | 広い範囲。要プレイテスト |
| カメラ初期位置 | スライム付近 | プレイヤーがパン可能 |

すべての敵・スライム・弾の座標はワールド単位で保持し、カメラ座標から逆算してゲーム状態を更新しない。

### 2.3 視覚表現

- スライム: 緑系の円/楕円 + 目、移動に合わせた軽い伸縮。
- 細菌: 赤系・紫系などの丸い図形と突起、種類を形または色でも区別。
- 攻撃: 見える速度で飛ぶ小さな弾。命中/被弾で簡単な演出。
- 選択した標的や回避方向を、任意のデバッグオーバーレイで表示できるように拡張可能。
- アートを作り込むことより、危険方向・位置関係・射程のわかりやすさを優先する。

## 3. オブジェクトと状態

### 3.1 スライム [初期値案]

| 属性 | 初期値案 | 説明 |
|---|---:|---|
| HP / 最大HP | 100 / 100 | 0で死亡 |
| 移動速度 | 160 unit/s | 方向ベクトルを正規化して移動 |
| 当たり判定半径 | 18 unit | 円形 |
| 攻撃射程 | 260 unit | 標的が射程内の場合に射撃 |
| 射撃間隔 | 15 simulation tick | 30TPSなら0.5秒 |
| 弾の速度 | 480 unit/s | ワールド上で移動 |
| 弾のダメージ | 10 | 整数で管理 |
| 攻撃対象 | 敵IDまたはNone | Pythonが指定 |
| 行動制御 | 移動方向 + 攻撃対象 | 同時に移動と射撃が可能 |

- スライムは瞬間移動できない。受け付けた方向に決められた速度で移動する。
- 方向 `(0, 0)` で停止。大きさ1を超える入力ベクトルはゲーム側で正規化する。
- 攻撃ボタン連打のような戦略は不要。射程内・クールダウン完了で自動射撃する。
- 標的未設定の場合、勝手なターゲット切り替えはしない。ただし高水準ヘルパーは「一番近い敵」を指定できる。

### 3.2 敵（細菌） [初期値案]

**追跡型 (Chaser)**

- スライムに向かって移動する基本敵。
- HP 20、速度 62 unit/s、当たり判定半径14、接触ダメージ 8。
- 接触中は一定間隔でダメージを与える（クールダウン30tick）。

**高速型 (Runner) [P1候補]**

- 追跡型より速いがHPが低い。回避の判断を難しくする。
- HP 10、速度 115 unit/s、当たり判定半径11、接触ダメージ 5。
- 登場時期と出現数はプレイテストで調整。実装が長引くならP1に据え置く。

**MVPに含めない敵**: 遠距離射撃、分裂、毒、状態異常、味方へのバフ、ボス。

### 3.3 弾

- プレイヤーが指定した攻撃対象が射程内にいる場合、スライムの現在位置から弾を生成する。
- 発射時に狙った方向へ直進する。追尾弾はMVP対象外。
- 弾・敵・ワールド境界の衝突を固定tickで判定する。
- 同じtickで複数に命中した場合はIDの昇順で順序を固定し、最初の1体に命中して消滅する。

## 4. 出現・難易度・スコア

### 4.1 ステージの時系列 [初期値案]

| 経過時間 | ゲーム上の狙い | 出現傾向 |
|---|---|---|
| 0〜10秒 | 最初の攻撃を見る | 少数の遅い敵 |
| 10〜20秒 | 接近への対処を意識する | 敵の数を増加 |
| 20〜40秒 | 単純な戦略の限界が見える | 四方から継続出現 |
| 40〜60秒 | コードの改善効果が現れる | 一定密度の敵群、必要なら高速型 |

- 出現時刻・位置・種類は、固定seedによる疑似乱数列または固定表から決定する。
- **再挑戦しても同じ出現順・同じ初期条件**にする。
- バランスの合格条件: 初心者用初期コードだけでは改善余地があり、適切な改良コードで60秒クリア可能であること。
- 正確な出現件数、HP・速度・弾数値は**暫定**。MVPのプレイテスト結果により調整し、同じバージョン内では固定する。

### 4.2 結果表示

- ステージクリア/失敗/中断の区別。
- 生存したtick・時間、撃破数、与ダメージ、被ダメージ、残HP。
- 「前回の実行との差分」を表示する機能はP1。MVPは数値を確認できればよい。
- 単一の総合スコアやランキングを優先しない。60秒生存の達成が勝利。

## 5. 決定論的シミュレーション（重要）

### 5.1 時計と更新周期 [確定方針 / 初期値案]

- **Simulation tick**: 30 tick/秒（論理更新間隔は `1/30秒`）。
- **Stage length**: 1800 tick = 60秒。
- **AI decision boundary**: 6 tickごと（tick 0, 6, 12, ...）。
- **Rendering**: 60 FPSを目標とするが、描画フレーム数はゲームルールに影響しない。
- **Game clock**: `tick` を唯一の経過時間の基準とする。

### 5.2 1tickの処理順序（固定）

1. 現tickがAI判断境界なら、tick開始時点の読み取り専用スナップショットをPythonへ送る。
2. Pythonからの行動指示を検証・確定する。応答処理中はシミュレーションtickを進めない。
3. スライムに移動指示を反映する。
4. 敵の移動・行動を決定して反映する（敵ID昇順）。
5. 攻撃クールダウンを処理し、条件を満たせば弾を生成する。
6. 弾を移動し、敵との命中を処理する（固定順序）。
7. 敵とスライムの接触を判定し、ダメージ・撃破・死亡を更新する。
8. 予定された敵の出現を処理する（出現した敵は次tickから行動）。
9. HPと制限tickをもとに勝敗を判定。未終了なら `tick += 1`。
10. 描画用状態を通知する。補間は表示専用。

実装の際はこの順序を1箇所のシミュレーション関数に閉じ込め、テストで保証する。

### 5.3 再現性の条件

- 固定seedの疑似乱数生成器を用い、`Math.random()` などの非管理乱数でゲームに影響する値を決めない。
- 物理演算に描画の `deltaTime` を使用しない。
- Entity ID・イベント順序・コレクションの走査順序を固定する。
- 状態更新は可能な限り純粋関数 `nextState = step(prevState, action, seedState)` として構成する。
- Python側に渡すゲーム時刻は実時間ではなく `tick`。時刻/外部I/O/独立乱数を使うコードの再現性は制約付きとする。
- Pythonが間に合わないからといって、AI判断を取りこぼしてゲームを先に進めない。原則応答を待つか実行エラーとする。
- カメラ・UI・ウィンドウ操作は `step()` の入力に含めない。
- **保証範囲**: まず「同じビルド・同じ実行環境・同じ状態/行動列」で再現を保証する。異なるOS/エンジン間のビット完全一致はMVPの必須条件にしない。

### 5.4 再現性の受け入れテスト

- 固定seed + 記録済み行動列を複数回適用して、各tickまたは一定間隔のstate hashが一致する。
- 同じ許可されたPythonコードを同じランタイム設定で複数回実行して、クリア/失敗・生存tick・撃破数・HPが一致する。
- ズームやエディタ位置を変えても同じ結果になる。
- 一時停止/再開を挟んでも、経過するゲームtickが同じなら結果が変わらない。

## 6. Pythonとゲームの境界

### 6.1 設計原則

- Pythonは **観測 (Observation) を読み、行動 (Action) を提出する**。Phaserオブジェクト、ゲーム本体のメモリ、敵HPを直接改変できない。
- Pythonの変数・リスト・辞書・関数・クラス・複数ファイルなど、標準的な書き方を広く使える設計とする。
- 初心者向けの短いヘルパーと、上級者向けの細かな位置・速度情報／移動指示を両方用意する。
- 公開Python APIはゲーム固有の `microgame` モジュールに集約する **[暫定API名]**。
- この節のコード例は**期待するゲーム側API案**。実装前に `PYTHON_API.md` で名前・型・例外を正式確定する。

### 6.2 読み取り専用の観測データ [MVP決定案]

```python
# 概念上の型。実装方式は未確定。
@dataclass(frozen=True)
class Vec2:
    x: float
    y: float

@dataclass(frozen=True)
class EnemyView:
    id: int
    kind: str
    position: Vec2
    hp: int
    distance: float

@dataclass(frozen=True)
class Observation:
    tick: int
    hp: int
    max_hp: int
    position: Vec2
    enemies: tuple[EnemyView, ...]
    nearest_enemy: EnemyView | None
```

- `enemies` はID昇順で固定。`nearest_enemy` の距離が同じならIDが小さい敵を優先。
- `distance` はスライム中心から敵中心までのユークリッド距離（unit）。
- 観測はAI判断境界のスナップショットであり、呼び出し中に裏で更新されない。
- Pythonで観測オブジェクトを変更してもゲーム内状態には影響しない。
- 敵IDは1回の実行中に一意で、倒された後は再利用しない。

### 6.3 行動データ [MVP決定案]

```python
@dataclass(frozen=True)
class Action:
    move_x: float = 0.0
    move_y: float = 0.0
    target_enemy_id: int | None = None
```

- `move_x` / `move_y` は移動方向。ベクトル長が1を超える場合は正規化。
- `(0, 0)` は移動しない。`target_enemy_id=None` は標的なし。
- 1回の行動に移動と攻撃対象指定を同時に含められる。
- 非数値、NaN、Infinity、存在しないIDなどは検証して安全に処理し、ログで知らせる（詳細は `PYTHON_API.md`）。
- 行動が正常に確定した後は、次のAI判断境界までその行動を保持する。
- 高水準API（`Action.flee` など）はこの基本Actionを返す補助機能である。

### 6.4 判断関数型AI

**用例（API案）**:

```python
from microgame import Action, set_ai

class SlimeAI:
    def decide(self, state):
        enemy = state.nearest_enemy
        if enemy is None:
            return Action()  # 停止・標的なし

        if enemy.distance < 120:
            # 初心者向けの高水準ヘルパー
            return Action.flee(
                state.position,
                enemy.position,
                attack_target_id=enemy.id,
            )

        return Action(target_enemy_id=enemy.id)

set_ai(SlimeAI())
```

- エントリーポイント `main.py` は実行開始時に1回評価され、`set_ai`でコントローラを登録する。
- 登録したAIの `decide(state)` はtick 0, 6, 12,...で呼び出される。
- 同じAIインスタンスを保持するため、`self` の変数に判断間の状態を保存できる。
- `decide` はActionを返す。Python処理中にゲームtickは進まない。

### 6.5 継続実行型スクリプト

**用例（API案）**:

```python
from microgame import Action, act, nearest_enemy, self_position

while True:
    enemy = nearest_enemy()

    if enemy is None:
        act(Action())
    elif enemy.distance < 120:
        act(Action.flee(
            self_position(),
            enemy.position,
            attack_target_id=enemy.id,
        ))
    else:
        act(Action(target_enemy_id=enemy.id))
```

- `main.py` の通常のPython文を上から実行する。ローカル変数・ループ・関数呼び出しの状態を維持する。
- `act(action)`や`attack_nearest()`等の行動関数はActionを提出し、次のAI判断境界までPythonを自動で休止する。ゲーム世界を呼び出した瞬間に更新する命令ではない。
- `wait_ticks(n)` は行動関数に必須ではなく、次の境界より長く待つ高度なタイミング調整に使う。
- **tick同期の定義**: 次回再開時刻は `現在tick + n` 以降の最初のAI判断境界（6の倍数）とする。例：tick 0で `wait_ticks(1)` はtick 6、`wait_ticks(7)` はtick 12で再開する。
- `n` は正整数とする。`wait_ticks(0)`や負数は説明可能なエラーとする。
- 状態確認やPython計算は固定されたObservation上で実行予算を消費するが、世界のsimulation tickは進めない。
- 行動関数、`wait_ticks()`、または処理終了で制御を返す前に実行予算を超えた場合、コード内容を特別判定せず同じ予算超過として一律停止する。
- Python側で`while True`を使えることは要件だが、中断可能な一般Pythonの継続実行を実現する手段は **[技術検証]**。Pyodide導入だけで成立するとは仮定しない。

### 6.6 ハイブリッドでの競合防止

- **同一スライムの行動制御権は1つ**: `set_ai()`で登録する判断関数型、または`act(Action)`等で行動を提出する継続実行型。
- 判断関数型を登録した後でも、メインスクリプトがログ出力・待機などを行う構成は許せる設計とする。
- 判断関数型が有効な間、継続実行側から同じスライムへ動作命令を出そうとしたら明確なエラーを出す。最後に実行された命令で黙って上書きしない。
- 将来複数スライムに拡張するときは、スライムID単位で制御権を持てる構造にする。

### 6.7 二層APIの例

| 種類 | 初心者向けヘルパー（案） | 上級者向け基本操作（案） |
|---|---|---|
| 敵取得 | `nearest_enemy()` | `get_state().enemies` |
| 回避 | `Action.flee(me, danger)` | `Action(move_x=dx, move_y=dy)` |
| 攻撃 | `attack_nearest()` | `act(Action(target_enemy_id=...))` |
| 位置 | `self_position()` | `get_state().position` |
| 時間 | 行動関数の自動待機 / `wait_ticks(n)` | `get_state().tick` |

高水準APIは「使わなくても攻略できる」ことが重要。攻略を隠したブラックボックスだけにしない。

### 6.8 ファイル構成とimport [MVP決定案]

```text
player-project/
  main.py        # 入口。起動時に評価される
  utils.py       # プレイヤーが自由に作成
  strategy.py    # プレイヤーが自由に作成
```

- エディタのファイル名と保存先をゲーム内ワークスペースとして管理する。
- `main.py` から `import utils` 等が動作することをMVP要件とする。
- ソースコードはローカルに保存され、実行時にPythonランタイムへ渡される。
- Python実行環境の仮想ファイルシステムがWindowsの任意フォルダへ直接アクセスしないようにする。
- 同じファイルは複数ウィンドウから開かれても単一のソースを参照する（状態の競合を避ける）。

## 7. Python実行時のエラーと制限

### 7.1 エラー設計

| 状況 | 挙動案 |
|---|---|
| `SyntaxError` | 実行開始を拒否。該当ファイルと行を表示。コード保持 |
| importの失敗 | ファイル名・不足モジュールを表示。修正可能 |
| `decide()`の実行時例外 | シミュレーションを一時停止してエラー表示。勝手に継続しない |
| 無効なAction | ログで理由を表示。原則、該当判断は安全な無行動として処理 |
| 無限ループ / 予算超過 | Workerの中断/破棄などで停止し、アプリは存続 |
| Stop | Python実行とゲームを終了し、編集可能状態へ戻す |
| Restart | ワールド・乱数・Python状態・tickを初期化して再実行 |

無効行動はエラーとして通知し、ゲーム状態が壊れないことを最優先する。厳密な停止/継続の基準は `PYTHON_API.md` で定義する。

### 7.2 性能と安全性

- Python実行はゲーム描画のメインスレッドから分離する。
- Web Worker + Pyodide は第一候補であるが、完全隔離を意味しない。
- 実行停止、割り込み、実行予算、メモリ上限、外部通信/OSファイルアクセスの制御可能性を技術検証する。
- シミュレーション結果に影響するPython側乱数は、ゲーム側で管理したseed利用を目指す。
- 実時間時刻、非同期I/O、無秩序な並列処理、外部アクセスなど、再現性を崩す機能はMVPでは原則無効または非保証とする。
- Pythonの一般構文が使えることと、すべての標準ライブラリが利用できることを混同しない。

## 8. フローティングエディタとカメラUI

### 8.1 画面レイヤー

```text
Electronデスクトップウィンドウ
  ├─ Phaser Canvas（常時、全画面の世界）
  │    ├─ 背景 / スライム / 細菌 / 弾 / エフェクト
  │    └─ Camera（ズーム / パン / フォーカス）
  │
  └─ React Overlay（ワールドとは独立）
       ├─ Floating Window Manager
       │    ├─ Monaco Editor: main.py
       │    ├─ Monaco Editor: utils.py
       │    ├─ Monaco Editor: strategy.py
       │    └─ Log / Debug Console
       ├─ File Explorer（折りたたみ可能）
       ├─ Run / Pause / Resume / Stop / Restart
       └─ HUD（HP / 60秒タイマー / 撃破数）
```

**左右固定の分割画面は採用しない。** プレイヤーが、ズーム・パン・エディタ配置を組み合わせ、自分に合う画面を作る。

### 8.2 ウィンドウ操作 [MVP決定案]

- ファイルを選んで独立したウィンドウを開く。固定個数を設けない。
- ウィンドウは移動・サイズ変更・最前面化・最小化・閉じる・再表示可能。
- 閉じる操作ではファイルを削除しない。保存されたコードは維持する。
- ウィンドウごとの位置/サイズ/開閉状態をローカル保存し、再起動で復元する。
- 初回は `main.py` 1枚を見やすい場所に開く。追加ウィンドウはプレイヤーが開く。
- 画面外へ完全に押し出されたウィンドウを呼び戻す手段を用意する。
- 最小サイズは読みやすさを損なわない範囲で制限する（具体ピクセル値はUI実装時に決定）。
- 同時ウィンドウ数は機能上の低い固定上限を設けないが、パフォーマンス確保のため非アクティブなエディタ描画を最適化する。

### 8.3 カメラ操作 [MVP決定案]

| 入力 | 挙動 |
|---|---|
| ゲームキャンバス上のホイール | ポインタ中心にズーム |
| Space + ドラッグ / 中ボタンドラッグ | カメラのパン |
| `F` | スライムへカメラを戻す（エディタ編集中は誤発火させない） |
| UIのフォーカスボタン | カメラをスライム付近に戻す |
| ズーム下限/上限 | 0.15倍 / 4.0倍を初期案とし調整可能 |

- エディタ内でホイール操作したときはエディタをスクロールし、背後のゲームをズームしない。
- エディタにキーボードフォーカスがある間、通常の入力文字をゲームのショートカットと解釈しない。
- UIの文字サイズ/配置はカメラ倍率に連動しない。
- カメラが大きくズームアウトして敵が点に見える場合は、視認性を損なわない描画を検討する（MVPでは基本表示でよい）。
- 自動でエディタとスライムの重なりを避ける配置機能はMVP必須ではない。まずはプレイヤーによる自由配置を重視する。

### 8.4 実行コントロールと編集

| 状態 | Run | Pause/Resume | Stop | コード編集 |
|---|---|---|---|---|
| 未実行 | 開始 | 無効 | 無効 | 可能 |
| 実行中 | 無効 | Pause | 可能 | 読み取り専用 |
| 一時停止 | 無効 | Resume | 可能 | 読み取り専用 |
| クリア/失敗 | Restart（初期化） | 無効 | 初期状態へ | 可能 |
| エラー停止 | Restart（再試行） | 無効 | 初期状態へ | 可能 |

- 実行中にコードを編集して即時反映する機能（hot reload）はMVP対象外。
- PauseはシミュレーションtickもPythonのゲーム時間も止める。リアルな描画はUI応答のため維持してよい。
- Restartでtick/seed/Pythonメモリ/ワールド状態をリセット。コードとウィンドウ配置は保持。
- ユーザーのコード・レイアウトを失わないことを優先する。

### 8.5 ログとデバッグ

- 出力ログは別のフローティングウィンドウとして開閉可能。
- Python `print()`、エラー、行動に関する基本ログを表示。
- 各ログに可能ならsimulation tickを付ける。エラー時はファイル名・行番号を添える。
- ログ大量出力によるUIの停止を避けるため、表示行数や頻度には上限を設ける。
- 高度なブレークポイント、ステップ実行、時系列リプレイはMVP後。

## 9. 初心者の自然な学習導線

### 9.1 最初のコード

初回 `main.py` には、まず短くて戦闘が発生するコードを入れる。例：

```python
from microgame import attack_nearest

while True:
    attack_nearest()
```

- 初回Runで敵へ攻撃する様子が見える。
- この戦略だけでは後半で苦戦し、`if`で回避したい動機を作る。
- 実際のサンプルはPython実行の技術検証が通ったAPIに合わせて調整する。

### 9.2 ヒントの見せ方

- 強制チュートリアルではなく、右クリックや小さな「ヒント」操作などで任意に表示する。
- 「`if`文を学びましょう」ではなく、「近づいてきた細菌から逃げてみよう」のような問題提示にする。
- サンプルはコピーして編集できる。初心者に最初から大きなクラス定義を書かせない。
- `for`や関数、クラスを使用しないコードでもクリアできる余地を残す。

### 9.3 上級者の遊び方

- 複数の敵の位置/速度を使った危険度評価。
- 予測位置や速度ベクトルを使った回避。
- 一定tick間隔での状態の記録と戦略変更。
- 独自の探索関数、クラス状態、複数ファイルへの分割。
- ただしゲーム内部のHPや乱数を直接改ざんすることは攻略として認めない。

## 11. MVP受け入れシナリオ

### シナリオA — 初回プレイ

1. 新規起動時に `main.py` のコードが表示される。
2. Runを押すとPythonが読み込まれ、スライムが自律的に敵を攻撃する。
3. 戦闘中にHP・タイマー・撃破数が更新される。
4. 敵に倒されたらリザルトが表示される。
5. Stop/Restart後、コードを変えて再挑戦できる。

### シナリオB — Pythonの自由度

1. プレイヤーが `utils.py` を作成して、関数やクラスを書く。
2. `main.py` からimportしてゲーム実行できる。
3. 判断関数型と継続実行型の両方で移動・攻撃を制御できる。
4. スライム行動を決める際、ゲーム固有の高水準ヘルパーに依存せず基本座標とActionだけで制御できる。

### シナリオC — 自由配置UI

1. 2つ以上のエディタを自由な位置へドラッグ・リサイズできる。
2. ゲーム世界はエディタの背後でも描画される。
3. カメラをズーム/パンしてスライムを見やすい場所へ移せる。
4. レイアウトを保存し、再起動時に復元できる。
5. エディタをスクロールしてもカメラが意図せずズームしない。

### シナリオD — 決定論

1. 同じ固定seed、同じコードで同じ初期状態から実行する。
2. 戦闘結果が複数回とも一致する。
3. 途中で画面ズーム・ウィンドウ位置を変更しても結果が変わらない。
4. リプレイ用に固定Action列を適用したとき、状態hashが一致する。

### シナリオE — 異常系

1. Python構文エラーのあるコードを実行してもゲーム本体はクラッシュしない。
2. 無限ループ/長時間計算を停止でき、コードは失われない。
3. 不正なAction/対象外敵IDは安全に処理される。
4. エラー後にStop/Restartして正常なコードを再実行できる。

### シナリオF — Windows配布

1. Windows用ビルドを生成する。
2. Python/Pyodideの実行に必要な同梱ファイルが不足していない。
3. インターネット接続なしで起動・エディタ表示・ゲーム実行・保存ができる。

## 12. 推奨の技術検証ゲート（実装Issueより先に確認）

1. **Python起動**: Electron内のWorkerでPyodideがオフライン起動する。
2. **判断関数**: `decide(state)` を同じ状態で繰り返し呼べる。
3. **継続実行**: 本物のPythonの `while` と行動関数の自動待機、任意の`wait_ticks`をゲームtickと同期して停止/再開できる。
4. **終了保証**: 特定構文の検出に依存せず、行動・待機・return前に実行予算を超えた任意のコードから制御を回復できる。
5. **複数ファイル**: `main.py` からゲーム内 `utils.py` をimportできる。
6. **再現性**: 同じコード・初期状態でPython状態とAction列が再現する。
7. **安全性**: PythonからホストOS・Electron権限・任意ネットワークへ意図せず到達できないよう制限可能か検証する。

**Go/No-Go方針**: 3・4・7に大きな問題があれば、ゲームロジックを大量実装する前にPythonランタイム方式を再設計する。Pyodide自体への固執より、「プレイヤーが普通のPythonでコードを書けること」と「ゲームが安定して動くこと」を優先する。
